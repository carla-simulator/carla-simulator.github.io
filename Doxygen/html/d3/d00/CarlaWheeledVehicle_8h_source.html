228 /// Two-wheeled vehicles (bikes/motorcycles) embed their rider as a
229 /// SkeletalMeshComponent (named RiderMeshComponentName) meant to sit on
230 /// VehicleMeshSeatSocketName. That positioning is still driven by
231 /// Blueprint graph logic left over from the UE4-to-UE5 port, and it
232 /// drifts the rider backward off the seat while the vehicle is moving.
233 /// Rather than rewrite that graph, OnRiderBoneTransformsFinalized (see
234 /// below) snaps the rider back onto the seat socket every frame, after
235 /// this component's animation has finished evaluating for that frame --
236 /// nothing runs afterwards that could undo it before render, regardless
237 /// of what the Blueprint graph or its animation does. Only takes effect
238 /// when IsTwoWheeledVehicle() is true and both component names resolve
239 /// to real components on this actor.
240 ///
241 /// This does not fully fix the drift by itself -- the rider's own Anim
242 /// Blueprint separately queries this same seat socket in its own Event
243 /// BlueprintUpdateAnimation, and that read intermittently races ahead of
244 /// the vehicle mesh's physics update for the frame (confirmed by logging
245 /// both reads: on the frames it happens, the Blueprint's read exactly
246 /// matches the PREVIOUS frame's real seat transform -- a one-frame-stale
247 /// read on some frames but not others, which looks like a pop, not a
248 /// continuous drift). See GetCachedVehicleSocketWorldTransform() below,
249 /// which the Blueprint should read instead of querying the socket
250 /// itself -- for this one and every other vehicle-mesh socket its Data
251 /// Gather reads.
252 UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "CARLA Wheeled Vehicle|Rider")
253 FName RiderMeshComponentName = TEXT("SkeletalMesh");
254
255 UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "CARLA Wheeled Vehicle|Rider")
256 FName VehicleMeshSeatSocketName = TEXT("Seat");
257
258 /// Chaos suspension has small, real, high-frequency vertical jitter on
259 /// the vehicle mesh every frame (visible as the rider's torso/hip
260 /// bouncing, the seat popping the rider up) -- physically real, not a
261 /// bug, but the seat-lock's hard snap transmits it 1:1 to the rider with
262 /// zero smoothing. This is the speed (see FMath::FInterpTo) used to
263 /// low-pass just the VERTICAL (Z) component of the cached base transform
264 /// that GetCachedVehicleSocketWorldTransform() extrapolates from --
265 /// purely cosmetic, applied only to what the rider reads, never to the
266 /// vehicle's actual physics transform. X/Y and rotation are never
267 /// smoothed (see OnRiderBoneTransformsFinalized's comment -- smoothing
268 /// those trails a moving target by more the faster the vehicle goes,
269 /// which looked exactly like the original slide bug). Higher = snappier
270 /// (less smoothing); lower = smoother but more vertical lag.
271 UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "CARLA Wheeled Vehicle|Rider")
272 float RiderSeatSmoothingSpeed = 10.0f;
273
274 /// Cached, extrapolated world transform of ANY socket on the vehicle
275 /// mesh (Seat, HandlerLeftSocket, HandlerRightSocket, LeftPedalSocket,
276 /// RightPedalSocket, ...), captured from OnRiderBoneTransformsFinalized
277 /// (which fires late enough in the frame to reliably see this frame's
278 /// real, physics-updated position -- confirmed by logging it against
279 /// the vehicle's actual movement, always smooth, never stale).
280 ///
281 /// The rider's Anim Blueprint should read this instead of querying the
282 /// vehicle mesh's sockets itself (directly, or via a vehicle-side
283 /// variable computed that way) for EVERY seat/handler/pedal target used
284 /// in its Data Gather: that independent read, from the Blueprint's own
285 /// Event BlueprintUpdateAnimation, intermittently races ahead of the
286 /// physics update and returns last frame's transform instead --
287 /// confirmed first on the seat (fixed the torso pop) and then on the
288 /// same pattern showing up on the handler/pedal sockets driving the
289 /// arm/leg IK (hands/feet still popping to a stale pose after the torso
290 /// fix). This trades that flickering race for a lag that's constant
291 /// instead of intermittent, then extrapolates it away using the linear
292 /// velocity it was cached with -- all vehicle-mesh sockets share that
293 /// velocity, moving rigidly together, so one shared velocity/timestamp
294 /// covers every socket looked up here.
295 UFUNCTION(BlueprintPure, Category = "CARLA Wheeled Vehicle|Rider")
296 FTransform GetCachedVehicleSocketWorldTransform(FName SocketName) const
297 {
298 // Extrapolating each socket's own cached translation in a straight
299 // line (the first version of this function) ignores the vehicle's
300 // ANGULAR velocity -- it yaws/pitches/rolls a little essentially all
301 // the time (steering, suspension travel), even on flat road. Seat and
302 // the handler/elbow sockets sit close to the mesh's own origin, so
303 // that rotation barely displaces them and the straight-line
304 // approximation looked like a full fix. Sockets far from the origin
305 // -- the pedals, down at the sides -- get swept a lot further by the
306 // same small rotation (lever arm), which is exactly the "still
307 // sliding, constant, like before" the pedals kept showing after
308 // torso/hands were confirmed fixed.
309 // Fix: extrapolate the vehicle MESH's own rigid-body transform
310 // (translation + rotation, both from its cached linear/angular
311 // velocity) instead of each socket individually, then re-place every
312 // socket at its fixed (skeleton-rigid) offset from that predicted
313 // mesh transform -- this correctly sweeps far-out sockets through the
314 // rotation instead of leaving them on their own straight line.
315 //
316 // Extrapolating from SmoothedVehicleMeshTransform (see
317 // RiderSeatSmoothingSpeed's comment) here, not the raw
318 // CachedVehicleMeshTransform -- that raw value is still used below,
319 // unsmoothed, to compute each socket's RIGID offset (a static
320 // skeleton relationship, smoothing it would just introduce a phantom
321 // wobble between sockets instead of removing one).
322 FTransform PredictedMeshTransform = SmoothedVehicleMeshTransform;
323 if (const UWorld* World = GetWorld())
324 {
325 const float TimeSinceCache = World->GetTimeSeconds() - CachedVehicleTransformsTimeSeconds;
326 // X/Y (world space) zeroed for the same reason as the linear
327 // velocity's Z above -- Yaw is by definition rotation around the
328 // WORLD Z axis (true regardless of the vehicle's current heading),
329 // so keeping only the world-Z component of this angular velocity
330 // isolates exactly the yaw-rate contribution this extrapolation was
331 // meant to correct for (steering), while dropping the noisy
332 // Pitch/Roll rates that would otherwise reintroduce the same
333 // full-body rider bounce through every far-off socket (pedals,
334 // handlers) via their own lever arm.
335 FVector AngularVelocityRadians = FMath::DegreesToRadians(CachedVehicleWorldAngularVelocityDegrees);
336 AngularVelocityRadians.X = 0.0f;
337 AngularVelocityRadians.Y = 0.0f;
338 const FQuat DeltaRotation = FQuat::MakeFromRotationVector(AngularVelocityRadians * TimeSinceCache);
339 PredictedMeshTransform.SetRotation((DeltaRotation * PredictedMeshTransform.GetRotation()).GetNormalized());
340 // Z zeroed out here -- CachedVehicleWorldVelocity comes straight from
341 // physics (GetComponentVelocity(), unsmoothed) and its own vertical
342 // component is exactly as noisy as the position jitter this function
343 // is smoothing away above, so adding it back in would reintroduce
344 // the same uniform full-body bounce through every socket at once.
345 // Only X/Y matter for this extrapolation anyway (that's what the
346 // one-frame lag at real driving speed needed); vertical lag of a
347 // frame is imperceptible, unlike horizontal lag at speed.
348 FVector VelocityForExtrapolation = CachedVehicleWorldVelocity;
349 VelocityForExtrapolation.Z = 0.0f;
350 PredictedMeshTransform.AddToTranslation(VelocityForExtrapolation * TimeSinceCache);
351 }
352
353 // LeftPedalSocket/RightPedalSocket sit on LeftPedalGeo/RightPedalGeo,
354 // whose rotation isn't animated in the usual sense -- the AnimGraph's
355 // Transform (Modify) Bone on that bone is Component Space + Replace
356 // Existing, wired only on Rotation Y (Pitch) from Pedal Y (Roll/Yaw
357 // left at literal 0) -- meaning the bone's ENTIRE component-space
358 // rotation, every frame, IS exactly FRotator(+-PedalRotationAngle, 0, 0),
359 // nothing else composed in. A first attempt here tried to track "how
360 // much has the angle changed since the cache" and add that as a
361 // delta -- that's extra arithmetic (and an extra chance to get a sign
362 // or composition order wrong) for a value that doesn't need tracking
363 // at all: PedalRotationAngle itself is never stale (it's our own
364 // TickActor state, not read from a racing physics/Blueprint source),
365 // so the pivot's rotation can be reconstructed outright from it
366 // instead of extrapolated. Only the pivot's POSITION still needs the
367 // cached-and-extrapolated vehicle motion above -- its own spin
368 // doesn't move its origin, only the vehicle carrying it does.
369 static const FName LeftPedalSocket(TEXT("LeftPedalSocket"));
370 static const FName RightPedalSocket(TEXT("RightPedalSocket"));
371 static const FName LeftPedalPivotBone(TEXT("LeftPedalGeo"));
372 static const FName RightPedalPivotBone(TEXT("RightPedalGeo"));
373 if (SocketName == LeftPedalSocket || SocketName == RightPedalSocket)
374 {
375 const FName PivotBoneName = (SocketName == LeftPedalSocket) ? LeftPedalPivotBone : RightPedalPivotBone;
376 const FTransform* CachedSocket = CachedVehicleSocketTransforms.Find(SocketName);
377 const FTransform* CachedPivot = CachedVehicleSocketTransforms.Find(PivotBoneName);
378 if (CachedSocket && CachedPivot)
379 {
380 const FTransform SocketRelativeToPivot = CachedSocket->GetRelativeTransform(*CachedPivot);
381 FTransform PredictedPivot = CachedPivot->GetRelativeTransform(CachedVehicleMeshTransform) * PredictedMeshTransform;
382 // The AnimGraph feeds LeftPedalGeo the negative of Pedal Y and
383 // RightPedalGeo Pedal Y directly (see the Pedals block).
384 const float SignedPedalAngle = (SocketName == LeftPedalSocket) ? -PedalRotationAngle : PedalRotationAngle;
385 const FQuat ComponentSpaceRotation(FRotator(SignedPedalAngle, 0.0f, 0.0f));
386 PredictedPivot.SetRotation((ComponentSpaceRotation * PredictedMeshTransform.GetRotation()).GetNormalized());
387 return SocketRelativeToPivot * PredictedPivot;
388 }
389 }
390
391 if (const FTransform* CachedSocket = CachedVehicleSocketTransforms.Find(SocketName))
392 {
393 return CachedSocket->GetRelativeTransform(CachedVehicleMeshTransform) * PredictedMeshTransform;
394 }
395 return FTransform::Identity;
396 }

398 /// The rider mesh's rest pose isn't authored to sit flush with the
399 /// socket's own local axes -- its component template ships with this
400 /// exact relative rotation baked in (no translation), so the seat-lock
401 /// composes it on top of the socket's world transform instead of using
402 /// the bare socket transform, which twisted the pose.
403 UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "CARLA Wheeled Vehicle|Rider")

406 /// Two-wheeled vehicles spin a decorative pedal/crank bone (in the
407 /// vehicle mesh's own Anim Blueprint, unrelated to the rider) via a
408 /// looping Timeline whose curve doesn't start and end at the same
409 /// value -- every loop the Timeline restarts, the bone's rotation pops
410 /// instantly back to the curve's start value instead of continuing
411 /// smoothly, and the rider's foot IK (which targets a socket on that
412 /// bone) pops along with it. Play Rate scales with vehicle speed, so
413 /// the pops get more frequent the faster the vehicle goes, and their
414 /// size is capped at the curve's fixed peak value -- both are the
415 /// exact symptoms reported ("teleports", "there's a cap").
416 /// GetPedalRotation() replaces that Timeline: an angle continuously
417 /// accumulated from real vehicle speed and wrapped with Fmod, which
418 /// never pops (359.9 degrees to 0.1 degrees is the same rotation, not a
419 /// discontinuity) the way a Timeline restarting to an unrelated value
420 /// does. Bind it directly to whatever currently reads the Timeline's
421 /// output (Engine Speed -> Pedal Y) in the vehicle Blueprint's Anim
422 /// Blueprint instead.
423 UFUNCTION(BlueprintPure, Category = "CARLA Wheeled Vehicle|Rider")
424 float GetPedalRotation() const
425 {
426 return PedalRotationAngle;
427 }
